# AWS S3

Not wired up — the shipped driver is [R2](r2.md). This is the complete diff to
switch, in one sitting. Nothing outside `src/storage/` and `env.validation.ts`
changes, because the `STORAGE_*` variable names are provider-neutral.

## 1. Create a bucket

AWS console → **S3 → Create bucket**.

- Name and region (e.g. `xpro-media`, `us-east-1`) — note the region, S3 needs a
  real one where R2 uses `auto`.
- **Block all public access: leave ON.** Serve via CloudFront or presigned URLs.
- Enable default encryption (SSE-S3 is fine) and versioning if you want recovery.

## 2. Create an IAM user and policy

**IAM → Users → Create user**, programmatic access, with a scoped inline policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::xpro-media/*"
    },
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::xpro-media"
    }
  ]
}
```

Object actions target `bucket/*`; `ListBucket` targets the bucket itself — mixing
those up is the usual cause of a puzzling `AccessDenied`.

On EC2/ECS/Lambda, prefer an instance or task role and drop the static keys: leave
`STORAGE_ACCESS_KEY_ID` / `STORAGE_SECRET_ACCESS_KEY` unset and let the SDK's
default credential chain resolve them (see step 5).

**`src/storage/storage.module.ts`** — the client options that actually differ:

```diff

-          endpoint: storage.endpoint,
-          forcePathStyle: true,
+          ...(storage.endpoint ? { endpoint: storage.endpoint } : {}),
+          forcePathStyle: storage.driver === 'r2',

             accessKeyId: storage.accessKeyId,
```

Leave the checksum options in place. They exist for R2 but are a no-op difference
on S3 — the SDK simply skips checksums it does not need.

`storage.service.ts` needs no changes at all.

## 4. Configure

```bash
STORAGE_DRIVER=s3
STORAGE_BUCKET=xpro-media
STORAGE_REGION=us-east-1
STORAGE_ENDPOINT=
STORAGE_ACCESS_KEY_ID=<access-key-id>
STORAGE_SECRET_ACCESS_KEY=<secret-access-key>
STORAGE_PUBLIC_URL=https://dxxxxxxxxxxxx.cloudfront.net
```

With public access blocked, `STORAGE_PUBLIC_URL` should be your CloudFront
distribution (or custom domain). If you are strictly presigned-URL-only, the bucket
URL `https://xpro-media.s3.us-east-1.amazonaws.com` still works as a base.

## 5. Using IAM roles instead of keys

Drop `credentials` from the client and the SDK resolves the default chain
(env → shared config → IMDS/task role):

```diff
-          credentials: {
-            accessKeyId: storage.accessKeyId,
-            secretAccessKey: storage.secretAccessKey,
-          },
+          ...(storage.accessKeyId && storage.secretAccessKey
+            ? {
+                credentials: {
+                  accessKeyId: storage.accessKeyId,
+                  secretAccessKey: storage.secretAccessKey,
+                },
+              }
+            : {}),
```

Then make the two key variables optional in the `required` list in step 3.

## R2 vs S3 at a glance

| | R2 | S3 |
| --- | --- | --- |
| `region` | `auto` | Real region, must match the bucket |
| `endpoint` | Account endpoint, required | Omitted — derived from region |
| `forcePathStyle` | `true` | `false` |
| Public URL | No default; custom domain or `r2.dev` | Bucket URL or CloudFront |
| Egress cost | None | Charged |
| Checksum headers | Must be `WHEN_REQUIRED` | Either works |
| Credentials | Static keys only | Static keys or IAM roles |

## Migrating existing objects

```bash
rclone sync r2:xpro-media s3:xpro-media --progress
```

Configure both remotes with `rclone config` (R2 uses the `s3` provider type with
`provider = Cloudflare`). Keep both `STORAGE_PUBLIC_URL` hosts serving until you
are confident nothing references the old one — stored URLs in your database will
still point at it.
